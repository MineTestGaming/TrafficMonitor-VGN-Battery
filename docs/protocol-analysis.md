# V-HUB 2.3.41 设备 Metadata 协议分析

调查日期：2026-11-25。本文先记录已安装 V-HUB 发布包的静态证据，再单独记录本会话后续通过原生 HID 查询得到的实测结果。静态分析阶段没有运行 V-HUB 或发送 HID 请求；后续实测只查询状态，没有修改设备配置或固件。静态接口存在不等同于所有字段已在本机读取成功。

## 连接方式必须分开识别

调查初期 Windows 蓝牙枚举中有 N75 `320F:5055` 和 R1SE+ `25A7:FA6C` 的配对记录。用户随后确认两台设备当前均使用 **2.4G 接收器**，后续 HID 实读也确认了这条通路。配对记录不能代表当前正在使用蓝牙，更不能直接当成 V-HUB USB/2.4G 私有协议的筛选条件。

- N75 PRO 在 V-HUB 中属于 `EvisionApi`。筛选模板 `Ro` 位于 `[286289, 286900)`，设备专属条目位于 `[289250, 289650)`。USB/有线为 VID `0x320F`、PID `0x5055`，2.4G 接收器为 VID `0x320F`、PID `0x5088`；Usage Page `0xFF1C`、Usage `0x0092`。具体产品名分别为 `VGN N75 PRO`、`VGN N75 PRO 2.4G Dongle`。同一 VID/PID/Usage 模板也被其他键盘使用，必须同时核对产品名及实际接口，不能仅凭 VID/PID 选中任意键盘。
- R1 SE+ 在 Compx 型号映射 `[18899000, 18900050)` 中由 **CID=2、MID=31 或 32** 识别，两者分别对应白色、黑色，标识为 `r1-se+`。VID/PID 表 `[189131, 191950)` 包含多个 Compx 设备和接收器；WebHID 过滤器使用 Usage Page `0xFF04`、Usage `2`。这不是原生 Windows 应打开的报告 8 collection，实际差异见下方实测章节。型号映射应由读取出的 CID/MID 再次确认。
- 在此发布包中搜索十进制文本 `vendorId:9639`、`productId:64108`（即 `25A7:FA6C`）均无结果。这只是对该文本筛选形式的有界搜索；结合 Compx 筛选表，不能证明 V-HUB 支持通过本机 R1SE+ 蓝牙 HID 端点使用 Compx 私有命令。

Windows 标准蓝牙电量/GATT 与以下 V-HUB 厂商协议是不同的数据通路。能在 Windows 中读到蓝牙电量，不代表能在同一连接中读取 DPI、回报率或充电状态。

## VXE R1 SE+：Compx 请求/响应

证据：基础报文类 `[138205, 139500)`、命令枚举 `[139500, 140600)`、传输层 `[174648, 175900)`、控制器 `[175900, 180500)`。

### 报文格式

V-HUB 通过 WebHID `sendReport` 发送，默认 **Report ID=8**。Report ID 与 16 字节 payload 是分别传入 API 的参数；移植到 Windows 原生 HID API 时，应依据对应 API 的约定处理前导 Report ID，不能把 WebHID 的 payload 索引直接套在含 Report ID 的缓冲区上。

| payload 偏移 | 长度 | 含义 |
| --- | ---: | --- |
| 0 | 1 | 命令码；响应按此字节匹配待处理请求 |
| 1 | 1 | `commandStatus` |
| 2 | 2 | EEPROM 地址，DataView 默认大端 |
| 4 | 1 | 有效数据长度 |
| 5 | 至多 10 | 数据 |
| 15 | 1 | 校验字节 |

校验字节为 `(85 - ((8 + sum(payload[0..14])) & 255)) & 255`。外层 `& 255` 对应写入单字节的截断。Report ID 的数值 8 计入校验和，但它不位于 WebHID payload 中。

电量读取命令为 `0x04`，构造时其余字段默认清零。因此静态推导的请求为 Report ID `08`，payload `04 00 00 00 00 00 00 00 00 00 00 00 00 00 00 49`。该格式随后用于原生 HID 查询并成功得到响应；响应证据见实测章节。

### 电量、充电和电压

`Battery` 类 `[148129, 148450)` 定义响应读取：

| payload 偏移 | 字段 | 已证实语义及限制 |
| --- | --- | --- |
| 5 | `batteryLevel` | 1 字节；UI 直接赋给电量 progress |
| 6 | `batteryCharge` | 1 字节；UI 以非零表示正在充电 |
| 7..8 | `batteryVoltage` | `getUint16` 默认大端；这里只能确认一个原始 16 位量 |

UI 调用链位于 `[18909000, 18910050)`：先读在线状态，再在需要时读 CID/MID，确认 CID=2 后读取电量。充电、电量字段确实被 UI 使用。`batteryVoltage` 在该文件中只出现于 getter 定义，未找到 UI 使用和单位换算；后续实测在对应字节得到非零原始值 3548，但 **其单位和物理含义仍未验证，不能标为 mV 或 V**。

### 其他可查询的静态接口

| 查询 | 命令/位置 | 可解释字段 |
| --- | --- | --- |
| 无线在线状态 | `0x03`；`[147762, 148129)` | 状态字节、3 字节 RF ID |
| 当前配置 | `0x0E`；`[149157, 149556)` | 配置编号 |
| 型号标识 | `0x10`；`[149556, 149769)` | CID、MID；R1SE+ 对应 2/31、2/32 |
| 固件版本 | `0x12`；`[149769, 150050)` | 两个字节拼接为四位十六进制字符串；不要擅自解释为语义版本 |
| 回报率与 DPI 档位 | EEPROM 读命令 `0x08`，地址 0，长度 6；`[152799, 153800)` | 回报率枚举、最大 DPI 档位字段、当前 DPI 档位字段 |
| DPI 配置和颜色 | 控制器 `[176800, 178700)` | 通过 EEPROM 分段读取 X/Y DPI 原始配置、扩展值、每档颜色 |
| LOD、性能选项 | `[153800, 154500)`、`[158258, 161400)` | 静默高度、去抖字段、Motion Sync、线性修正、纹波控制、传感器休眠等原始配置 |

回报率枚举在 `[144000, 145600)`：`1→1000Hz, 2→500Hz, 4→250Hz, 8→125Hz, 16→2000Hz, 32→4000Hz, 64→8000Hz`。这些是协议族的映射，**不是 R1 SE+ 支持全部回报率的证明**。DPI 档位字段不是已经换算好的实际 CPI 数值，需结合 DPI 配置表和具体型号再解码。

存在主动状态通知 `0x0A`，其数据字节为字段变化 bitmask（DPI、回报率、配置、灯效、电量等），见 `[152350, 152799)`。它是“哪些字段发生变化”的通知，不等同于通知中直接包含所有字段的最新值。

以上为静态接口清单。后续只对其中的在线状态、CID/MID、电量、固件原始字节、回报率/DPI 档位原始配置进行了成功查询；其余不能描述为已从本机读取成功。

## VGN N75 PRO：Evision 请求/响应

证据：传输层 `[256811, 258005)`、报文类和命令枚举 `[258005, 259450)`、电量结构 `[260972, 261218)`、控制器 `[266804, 274500)`。

### 报文格式

V-HUB 使用 `sendReport`，**Report ID=4**。`EvisionApi.init` 按连接方式设置共享报文大小：有线 payload 63 字节/数据块 56 字节，2.4G payload 31 字节/数据块 24 字节。这里描述代码初始化后的尺寸，实际原生实现仍必须以 HID collection 的 ReportByteLength 和连接端点核验，不能凭产品名强发固定长度。

| payload 偏移 | 长度 | 含义 |
| --- | ---: | --- |
| 0..1 | 2 | 小端请求序号，通常 1..65535 循环；响应据此匹配 |
| 2 | 1 | 命令码 |
| 3 | 1 | 对分段读取命令为请求数据长度 |
| 4..5 | 2 | 对分段读取命令为小端数据偏移 |
| 6 | 1 | 此处尚未确定的保留字节 |
| 7 起 | 连接相关 | 响应数据区域 |

此报文类未定义像 Compx 那样的尾部校验；不能将两个协议的校验规则混用。清屏命令有特殊序号逻辑，但电量读取不涉及该功能。

### 电量和充电

`getPowerInfo → DevicePowerInfo.create` 发送命令 **`0x1A`**，其余字段默认清零，传输层填入请求序号。响应：

| payload 偏移 | 字段 | 已证实语义及限制 |
| --- | --- | --- |
| 7 | `power` | 原始电量字节 |
| 8 | `battery` | UI 使用 `!=0` 作为充电状态 |

UI 实际消费见 `[18914500, 18915700)`：电量非零且不等于 100 时，会向上取到接近的 5 或 10 的倍数。因此 V-HUB UI 的显示值未必等于设备原始返回值。插件可保留原始有效百分比并标明来源；不能把此 UI 取整解释为电池硬件只有 5% 精度。代码还以电量非零控制在线呈现，因此零值可能有无效/无设备歧义，必须结合运行证据再确定。

电量结构中未见电压、电流、容量、剩余续航字段；不应据此虚构这些 Metadata。

### 固件与配置 Metadata

- 固件：命令 `0x03`，`getKeyboardInfo` 位于 `[267750, 268650)`。有线一次读取 38 字节；2.4G 分为 24 和 14 字节。组装后的第 36/35 字节依此拼为十六进制文本，再按十进制解析得到 `firmwareVersion`；这是厂商现有的显示算法，具体版本含义仍需本机响应验证。
- 键盘配置：命令 `0x05`，实现位于 `[268611, 274500)`，可读取 profile、灯效模式、亮度/速度/RGB、两级休眠参数、Win 键锁、6 键标志、轮询率枚举、重复速率/延迟、logo 灯配置、按键延迟等原始字段。有线一次读取；2.4G 按 24+24+8 字节读取。某些保留字段按键盘型号有不同解释，不能直接跨型号命名。
- 按键矩阵/Fn 矩阵/灯位矩阵也有读取接口，但它们属于配置数据，不是实时键盘输入采集；对于电量插件通常无需读取。
- 产品名、VID/PID、Usage Page/Usage、端点路径及有线/接收器分类可从主机枚举获得；它们不是 `0x1A` 电量响应中的字段。

## 本机 2.4G 原生 HID 实测

本节为静态分析之后的独立运行证据。`BatteryCollector` 使用 SetupAPI/HID API 枚举目标厂商 collection，发送上述只读查询，保存 `.analysis/hid-live.ini`。审阅到的这份快照 SHA-256 为 `B3CE7A31A051DA286B56C9F6101A702FD4B478AB97B7E4DCFBAAB79810D9DC45`；文件可能被后续采样覆盖，以下值仅代表该次采样，不代表持续当前状态。`observed_ms` 是本次 Windows 启动后的单调毫秒数，不是 UTC 时间。

| 项目 | VGN N75 PRO | VXE R1 SE+ |
| --- | --- | --- |
| 原生产品名 | VGN N75 PRO 2.4G Dongle | VXE Mouse 1K Dongle |
| 制造商字符串 | Telink | Compx |
| USB VID:PID | `320F:5088` | `3554:F58E` |
| USB revision 原始值 | `0100` | `0110` |
| 原生 collection Usage Page:Usage | `FF1C:0092` | `FF02:0002` |
| InputReportByteLength / OutputReportByteLength | 64 / 64 | 17 / 17 |
| 查询 Report ID / 电量命令 | `04 / 1A` | `08 / 04` |
| 电量原始百分比 | **56%** | **20%** |
| 充电字段 | 0，未充电 | 0，未充电 |
| 采样 observed_ms | 68801796 | 68801781 |

这里的 Windows 原生缓冲区 **包含第 0 字节 Report ID**。因此对应上述 WebHID payload 的字段整体后移一字节：N75 电量为原生 byte 8，充电为 byte 9；Compx 电量为 byte 6，充电为 byte 7。

本次实测明确了两项仅靠 WebHID 静态筛选表无法确定的实现细节：

1. N75 2.4G 的厂商 payload 逻辑长度为 31，但原生 HID collection 的报告缓冲区长度为 **64**。实际发送按 OutputReportByteLength 补零，接收也按 InputReportByteLength 分配。不能将 `31+1=32` 直接当作此端点允许的 Windows WriteFile 长度。
2. Compx WebHID 设备筛选使用 `FF04:2`；本机原生 Windows 对应的 `FF04` collection 只有 feature 能力，不能承载这里的报告 8 输入/输出。实测成功的原生 collection 为 **`FF02:2`，输入/输出均 17 字节**。WebHID 可将同一物理 HID 接口的 collections 汇总，Win32 打开的设备路径对应单个 collection，因此应核对 HID capabilities，而不是照抄 WebHID filter。

保留的原生响应摘录如下（N75 仅列前 10 字节，其后均为零；鼠标列完整 17 字节）：

```text
N75 电量：04 28 DD 1A 00 00 00 00 38 00 ...
R1 型号：08 10 00 00 00 03 02 1F 34 00 00 00 00 00 00 00 E5
R1 电量：08 04 00 00 00 02 14 00 0D DC 00 00 00 00 00 00 4A
R1 档位：08 08 00 00 00 06 01 54 04 51 02 53 00 00 00 00 40
```

由鼠标响应还可确认：

- 型号查询得到 `CID=2、MID=31`，与静态 R1 SE+ 型号映射一致。
- 固件命令 `0x12` 返回原始字节 `03 00`；未赋予额外语义版本含义。
- EEPROM 地址 0、长度 6 的读取成功，回报率原始枚举为 `1`，按静态映射对应 **1000Hz**；当前 DPI 档位原始值为 `2`。未读取实际 DPI 配置表，不能据此给出实际 CPI 数值，也不擅自将其称为第几档。
- 电量报文中原始电压字节为 `0D DC`，大端数值 **3548**。响应 dataValidLen 为 2，而电压位于其后的字节，因此即使字节非零，也继续只保留原始值，不据此推断电压单位或有效性。

成功采样证明本机两台设备可独立于 V-HUB 运行进程，经 2.4G 接收器查询这些字段。它没有证明蓝牙、有线、其他固件版本、充电切换、休眠恢复或所有配置命令均已验证；TrafficMonitor 内的加载、绘制和退出则属于另一层验收。

## 已确认、推断和待验证

**已静态确认**：上述报文格式、命令码、解析偏移、V-HUB 对电量和充电字段的使用、N75 的型号筛选、R1 SE+ 的 CID/MID 映射。

**本机运行已确认**：两台 2.4G 接收器的产品名、VID/PID、原生报告 collection 和报告长度；N75 56%、R1 SE+ 20%、两台未充电；R1 SE+ CID/MID、固件原始字节、回报率原始枚举和 DPI 档位原始值。数值为上述单次快照。

**仍待运行验证**：蓝牙连接上的厂商协议支持、有线通路、充电状态切换、Compx 电压单位及有效性、低电/休眠/断连时返回行为、N75 固件和其他键盘配置、鼠标实际 DPI 数值/颜色/性能配置以及所有可选命令在本机固件中的支持程度。

实现应优先使用本机已验证的数据源，在状态中保留来源与采样时间，对无效、断连和过期数据作区分。若采用 USB/2.4G 厂商读取，只发送已确认的查询命令；不为获取电量初始化整套驱动、不下载驱动状态、不恢复出厂、不配对、不写 EEPROM 或固件。
